Quantum-kernel reliability · c2q_clique (QAOA)

The clique kernel never lies — but past ~16 qubits, it mostly just runs out of time before it can tell you anything.

Same soundness property as the k-coloring kernel: across every infeasible case tested, it never once claimed a clique that wasn't there. What's different is the failure mode as problems grow — reliability and wall-clock cost degrade together, and the wall-clock cost hits a wall (minutes per run) well before the 28-qubit hard limit the code itself enforces.

Sound, every test

0 false positives across 27 infeasible-case trials (star graphs and empty graphs, requesting cliques the graph provably doesn't have). decode_clique verifies every returned set before reporting a size, the same way decode_kcolor did. Everything below is about how often it finds a clique that does exist, and how long that takes as the graph grows.

01

Completeness collapses faster on the realistic case than the trivial one

Two very different tests, same qubit count. Trivial: a complete graph, where any subset is automatically a valid clique, so this isolates whether QAOA can even converge on selecting the right number of qubits. Planted: a genuine size-4 clique buried in an otherwise sparse, mostly-unrelated N-vertex graph — the realistic "does this subgraph exist" question. Both at the default layers=2, 10 seeds per point.

The gap is the finding. Qubit count alone doesn't predict difficulty — a size-4 target in a 16-qubit search space (0% hit rate) is categorically harder than selecting all 16 qubits in a 16-qubit trivial case (70%), even though the trivial case asks for a bigger answer. The QUBO landscape's shape, not just its dimension, is what QAOA at layers=2 struggles with.

02

The wall-clock cliff arrives well before the qubit ceiling

check_qubit_limit enforces a hard stop at 28 qubits (a statevector needs ~4GB there). In practice, nobody gets close — cost grows steeply enough that N=22 alone took 4 minutes for a single seed. N=4–16 are 10-seed averages; N=18–22 are single-seed spot checks (multi-seed statistics stopped being practical to collect).

N=16→18 roughly quadruples the time; N=20 and N=22 are where it stops being close to linear-in-qubits at all. And it's not just slow out there — both single-seed N=20 and N=22 checks also failed to find the target clique (13/20 and 21/22 respectively), so the extra minutes don't even buy a reliable answer.

03

More QAOA depth fixes it at fixed N — cheaply

At N=16 (complete graph, request K=16), layers=2 and layers=4 both landed at 40%. layers=6 hit 100% (5/5), for barely more time than layers=4 — depth costs linearly, not exponentially, since it doesn't touch qubit count. 5 seeds per bar.

04

A subtlety: the returned size doesn't always match the requested K

c2q_clique(g, k=-1) defaults to targeting K = N−1. On a complete graph, the QUBO's constraint encoding only softly prefers exactly K selected vertices (a penalty term, not a hard constraint) — and since every extra vertex in a complete graph adds another valid edge (a bonus in the QUBO), the optimizer can drift to selecting more than K when doing so stays clique-valid.

Not a soundness problem — whatever's returned is still verified as a genuine clique. But a caller expecting objective == K specifically (rather than "at least K, and still valid") would be surprised by this on dense graphs.

Practical limits, summed up

Untested> 22extrapolated cost: hours+ per run

Same overall shape as the k-coloring kernel's findings: sound, never wrong when it answers “yes,” but completeness is the real constraint, and here it's compounded by a wall-clock cost that turns exponential well inside the code's own qubit ceiling. Any bridge built on this kernel needs the same kernel-first, mandatory-classical-fallback shape the kcolor bridge uses — and probably a size cutoff well under 16, not 24, given how early the hard-case failure sets in.
