Quantum-kernel reliability · c2q_maxcut (QAOA)

The MaxCut kernel is honest by construction — whether it finds the true cut depends on the graph's shape, not its size.

Every bit-assignment QAOA can return is already a valid 2-partition, so there's no invalid-answer failure mode to guard against here — unlike every other kernel in this set. What replaces it: a graph with obvious structure (a ring) gets solved perfectly at every size tested; a graph with none (sparse and irregular) collapses to a coin flip by N=8 and to zero by N=14, at the exact same qubit count.

No invalid-answer mode, by construction

0/10 negative objectives in a direct check, and structurally impossible to get more: decode_maxcut just counts cut edges for whatever partition comes back — there is no constraint a bitstring can violate. That single fact reshapes everything else below: MaxCut's problem was never soundness, only how often (and how fast) it finds the best cut rather than a cut.

Regularity predicts completeness far better than qubit count does

Three graphs, same qubit count at each point on the x-axis, same layers=2, 10 seeds per point, ground truth from an exhaustive classical search (or the closed-form balanced-bipartition formula for the structured cases). Cycle: every vertex has degree 2, a trivial two-coloring exists. Complete: maximally symmetric, but touching every other vertex. Random: sparse (density 0.4), no exploitable symmetry — the realistic case.

Same qubit count, three completely different outcomes. The ring graph's QAOA landscape has a symmetry the optimizer can exploit at every scale tested; the random graph's doesn't, and completeness falls off a cliff well before qubit count becomes the limiting factor. This is the same "shape, not size" finding the clique kernel showed — but starker here, because MaxCut's soundness is trivial by construction, so shape-dependence is the entire story, not one factor among several.

Wall-clock cost grows the same way — but roughly a third as fast as clique's

Same exponential shape seen in every kernel tested so far — but MaxCut reaches N=22 in 82 seconds where clique needed 240 seconds for the same N. The QUBO here has no penalty terms (any bitstring is valid), which means a simpler cost Hamiltonian and, apparently, a real wall-clock advantage — not just a correctness one.

03

Unlike clique, more QAOA depth does not reliably rescue the hard case

Clique's stress test found that tripling layers turned a 40% hit rate into 100% at fixed N, for under 2× the time. Testing the same lever here, on the random graph at N=14 (the point where completeness had just collapsed to near-zero above): it does not repeat. 5 seeds per bar.

Hit rate vs. QAOA depth at fixed N=14

Random sparse graph (density 0.4), same instance as §01

20% → 40% → 20% — noise around a low baseline, not a trend. Depth cost the same roughly-linear amount it did for clique (7.2s vs 4.5s, about 1.6×), but bought nothing durable in return. The two kernels' QUBO landscapes respond differently to extra circuit depth, and this specific graph instance's difficulty isn't a depth problem the way clique's was — more evidence that instance shape, not a single dial like layers or qubit count, is what governs whether QAOA converges here.

Practical limits, summed up

Unreliable14–16random-graph hit rate reaches 0%; extra depth didn't fix it
Impractical18–2210–82s per run, single spot checks all missed the true optimum

No soundness axis to report here — that's the one respect in which this is the simplest kernel of the four QAOA-based ones evaluated so far. What replaces it is a completeness story that's more sensitive to graph shape than any other kernel tested: a structured instance solves perfectly at sizes where an irregular one has already collapsed to 0%, and unlike clique, adding QAOA depth doesn't reliably close that gap. Any bridge built on this kernel should weight graph regularity, not just node count, when deciding whether to trust a kernel-first attempt over a classical fallback.
